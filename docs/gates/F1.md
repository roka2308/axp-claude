## The slice

`Login → Project → Matomo Connection → Site → Semantic Metric → Dashboard →
Widget → Matomo Query → Viewer` runs end to end. The reference demo of §27 is
the canonical fixture: a securely initialized instance, local auth, the tenant
`Corporate Communications Demo`, the project `Employee Portal`, a mock Matomo
adapter, one site, a stored capability result, Visits and Pageviews as
normalized metrics, and the published dashboard `Portal Overview` with a KPI
card, a time series and a top-pages table.

## Acceptance criteria (Master Specification §27)

| Criterion                                  | Result | Evidence                                                                                                                                                                                                                  |
| ------------------------------------------ | ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server-side tenant/project authorization   | pass   | a project viewer is refused a tenant route and a publish (403); an unknown project answers 404; an unauthenticated read answers 401; cross-tenant denial is covered case by case in `tests/integration/analytics.test.ts` |
| No Matomo credentials in the browser       | pass   | no API response and no rendered page contains the token or the string `token_auth`; the credential is stored as AES-256-GCM ciphertext and has no read path                                                               |
| No analytics results in MySQL              | pass   | after rendering, none of the measured values and none of the dimension labels appears anywhere in the product store; rendering writes no row at all                                                                       |
| Dashboard config survives restart          | pass   | the whole stack is stopped and started again; the dashboard renders identically through a fresh session                                                                                                                   |
| Published stays stable while draft changes | pass   | an edited draft leaves the published version untouched; the preview shows the draft through the same builder; a stale draft write is refused with 409                                                                     |
| Widget loading/empty/error states          | pass   | `ready`, `zero`, `empty` and `unavailable` demonstrated through the mock scenarios; a failed source leaves the dashboard frame intact                                                                                     |
| Semantically correct comparison            | pass   | the comparison period has the same length and ends immediately before the range; the stated change matches the two values beside it; the comparison series is aligned point for point                                     |
| Relevant audit events                      | pass   | bootstrap, login, tenant, project, user, role assignment, connection, capability refresh, site import, site assignment, dashboard creation and publication are all recorded                                               |
| Correlation ID through request → Matomo    | pass   | a stub Matomo records the outbound calls: every one carries `x-correlation-id` from the inbound request, and the credential is in the POST body, never in a query string                                                  |
| Bootstrap only once                        | pass   | a fresh instance reports `uninitialized`; the token is single-use and a replay is refused                                                                                                                                 |
| Keyboard/focus smoke test                  | pass   | the viewer controls are reachable and operable by keyboard, and a keyboard-focused control has a visible focus ring (`:focus-visible`)                                                                                    |
| Responsive viewer                          | pass   | at 390×844 the grid reflows into one column with no horizontal overflow, the chart stays inside the viewport, and the time range still changes                                                                            |
| Capability-driven Matomo status            | pass   | compatibility is derived from 17 probe results, never from the version string; the version travels beside the conclusion                                                                                                  |

Each setup section is gated on the capability it needs, not on one blanket
permission: a tenant administrator connects Matomo and assigns the site, a
dashboard editor creates and publishes the dashboard, and each is told which
step belongs to the other role. `GET /projects/:id` returns the capabilities
the server granted, so the web app hides what it is not offered and never
re-derives an authorization decision.

## Defects found and fixed during the gate

| Defect                                                                        | Impact                                                                                                                                      | Fix                                                                                                                                                    |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Gate scripts killed a Windows shell wrapper instead of the server process     | The "survives a restart" step could pass against the processes it believed it had stopped, and `next build` later failed with `EBUSY`       | Servers are spawned without a shell, stopped with `taskkill /T`, and the stack refuses to start while a port still answers                             |
| The E2E suite signed in once per test case                                    | The sixth sign-in hit the login rate limit, so a working brute-force safeguard looked like a product failure                                | `tests/e2e/auth.setup.ts` signs in once and hands the session to the specs that only need to be signed in                                              |
| `tests/integration/persistence-rules.test.ts` asserted the Phase 0 table list | Intended: the list is the review moment for every new table                                                                                 | Extended deliberately with the ten Phase 1 tables, plus assertions that the credential is ciphertext-only and a dashboard snapshot holds configuration |
| Twenty source files were not Prettier-formatted, one script had CRLF endings  | `npm run verify` failed at `format:check`                                                                                                   | Repository formatted; the ESLint script override now also covers `apps/*/scripts/**`                                                                   |
| The project page loaded the dashboard list for every caller                   | A tenant administrator holds no `dashboard.read_published`, so opening a project answered 500 — an additive-roles rule surfacing as a crash | Each section asks for the capability it needs and explains its absence; `GET /projects/:id` now returns the granted capabilities                       |

## Remaining for Phase 1

Nothing. The one item folded into Phase 2 is "add KPI / Time Series / Top Pages
Table", because adding a widget is the widget gallery and the Inspector — the
two central deliverables of Phase 2 (D2/D3). Building a throwaway version of
them here would have been work to delete.

says so rather than pretending otherwise.
